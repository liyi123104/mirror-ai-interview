# 二十题自测（按本项目真实实现回答）

> 答不上来的，回去看对应文件。每一题都标了「看哪」。

### 1. 为什么拆两个服务？不拆行不行？
业务要事务、并发、鉴权，Java 的生态和稳定性更合适；PDF 解析、向量检索、提示词编排，Python 生态更全、迭代更快。
不拆也能跑，但会把两件不同节奏的事绑在一个进程里：改一句提示词要重新发版 Java，评分要并发时又受同一个线程池限制。
看 `docs/architecture.md`。

### 2. AI 服务为什么不连数据库？
为了让它是**无状态**的：来一个请求，带上简历和岗位要求，返回题目或分数，不碰任何持久化。
好处是能横向扩容（加副本不用考虑连接池），也保证了「AI 侧改坏了不会污染业务数据」。
代价是每次要多传一点上下文（简历 JSON 只有几百字节）。
看 `ai/app/routers/interview.py` 的 `NextRequest`。

### 3. 两边靠什么保证接口不出错？
一份手写的内部契约 `docs/ai-contract.md`（七个接口、字段名小驼峰、统一包体 `{code,message,data}`），
加上 Java 侧唯一的出口 `AiClient`：所有调用都经过它，统一加 `X-Internal-Token` 和 `X-Trace-Id`，
统一拆包判断 `code != 0`，4xx 把 FastAPI 的 `{"detail": ...}` 转成业务异常。

### 4. AI 服务挂了，用户看到什么？
`AiClient` 捕获 `ResourceAccessException` → 抛 `AiUnavailableException` → `GlobalExceptionHandler` 统一返回
`{"code":5030,"message":"面试服务暂时不可用，请稍后重试"}`，HTTP 503。
**不会卡 90 秒**：连接超时是 3 秒。`scripts/acceptance.ps1 -DowngradeOnly` 可以复现。

### 5. 评分为什么要打两次？
一次是「模型这一次的判断」，两次能发现「这次判断本身就不稳」。
差值 0–1 取均值（high），差 2 取均值（mid），差 ≥3 打第三次取中位数（low）。
本机实测：温度 0 时两次结果完全一样，一致性 100%——双评在这里的价值是兜住偶发抖动，不是「从 60 抬到 90」。

### 6. 温度设 0 为什么还不完全一致？
温度 0 只是「每次取概率最高的 token」，服务端批处理、浮点误差、模型版本热更新都可能带来微小差异。
实测：温度 0 三轮完全一致；把温度调到 0.8，最大差值 0.5。见 `docs/eval-log.md` 的 v5。

### 7. 证据校验误判了怎么办？
`validate_evidence` 要求 evidence 的前 12 个字（去空白）出现在回答里。
**两次都校验失败才降级**：单次偶发失败很常见，两次都失败才说明模型在编。
降级的后果只是 `confidence=low`，分数保留，不会丢数据。

### 8. 追问为什么必须引用原话？
不引用就会变成「你能详细说说吗」这种套话，追问没有价值。
规则：追问必须包含回答里的连续片段（短回答 2 字、长回答 3 字），否则丢弃并改出一道新题。
`ai/app/services/interviewer.py` 的 `_cites` + `tests/test_interviewer.py`。

### 9. 为什么评分放在「提交回答」时而不是「结束面试」时？
两个原因：一是可以立刻把分数写进 `turn`，报告阶段不用重复调用（省钱）；
二是结束时要并发生成复盘，如果评分也堆在那里，报告会从 10 秒变成半分钟。
看 `InterviewService.answer` 的评分段。

### 10. 报告生成为什么要并发？
八题串行调复盘接口要 30–40 秒，并发只要 5–8 秒（实测整场 41 秒，含八题问答）。
用 `CompletableFuture.supplyAsync` + `join`，失败的单题有兜底文案，不影响整份报告。

### 11. 单场成本 0.18 元怎么算的？
每次 AI 调用的 usage 都落 `cost_log`（scene = question / score / report）。
最近一场：score 0.1681 + question 0.0059 + report 0.0106 ≈ 0.185 元，输入 5 万 token 左右。
四维双评是 8 次调用/题，想省钱就把 `mirror.ai.score-dimensions` 改成两维。

### 12. 跨语言排查问题，你怎么定位？
先分层：`curl` 直接打 Python 的 `/ai/health` 和 `/ai/interview/next`（带 token），通了说明 AI 侧没问题；
再 `curl` Java，看返回是 5030（AI 不可用）还是 4000（业务错误）还是 5000（Java 自己炸了）。
`AiClient` 每个请求都有 8 位 `traceId` 打在日志里，两边日志用同一个 id 对。

### 13. Python 重启后索引丢了怎么办？
内存索引，重启即空。Java 在 `ApplicationReadyEvent` 时把题库全量推一次（`StartupSync`），
新增题目时增量推（`QuestionService.create`），删除时同步删索引。
实测：重启 Python 后 size=0，重启 Java 后 size 恢复为题目数。

### 14. 为什么没用向量库？
几百道题全量装内存，一次检索挨个算余弦也就几毫秒，引入 Milvus/FAISS 只会多一个部署件和一个故障点。
一万条以上再换。这个取舍写进了 `docs/architecture.md`。

### 15. 面试状态为什么不能放 Python？
状态要事务：存回答和存题目必须同生共死；还要做越权检查（sessionId 是不是你的）、并发控制（同时提交两次）。
这些是 Java 和 MySQL 擅长的。Python 那边只做「无状态计算」。

### 16. 两个服务怎么部署？端口怎么暴露？
Nginx（80）→ server（8080）→ ai（8000），只有 80 对外。
容器间用服务名（`http://ai:8000`），`INTERNAL_TOKEN` 两边一致。
Nginx 上 `/api/interview/` 必须 `proxy_buffering off`，否则流式会变「卡十秒整段蹦」。
见 `docker-compose.yml` 和 `web/nginx.conf`。

### 17. 一百人同时面试，哪里先撑不住？
先撑不住的是模型侧（并发 8 次/题 × 100 人），会被限流；其次是 SSE 占用的 Tomcat 连接（有 180 秒超时兜底）。
应用侧可以先做：评分维度降到两维、`SCORE_WORKERS` 调小、SSE 改成轮询。
MySQL 反而最不容易是瓶颈。

### 18. 换成纯 Java 会损失什么？
PDF 解析（pypdf）、向量化（bge-m3 的 Python 客户端）、提示词调试生态都要重写或用 JVM 版本替代，
迭代速度会明显下降；好处是少一个服务、少一次网络跳转、部署更简单。
这个项目选择「业务用稳的、AI 用快的」。

### 19. 你觉得这个设计最大的缺陷是什么？
评分口径和人工标注的一致性只有 0.60：模型偏保守，两条 5 分回答被压到 3–4 分。
根因是我没有更大规模的标注集（只有 10 条），无法可靠地区分「提示词问题」和「标注不一致」。
另外 Docker 部署还没在真实服务器上验证。

### 20. 如果重做一次，你会改什么？
1. 先做标注集（50–100 条），再动提示词，避免 10 条样本上过拟合；
2. 评分改成「逐维度流式返回」，前端能先看到技术深度再等其余维度；
3. 把内部契约用 JSON Schema 固化，Java 侧自动生成 DTO，减少手写字段名出错。
